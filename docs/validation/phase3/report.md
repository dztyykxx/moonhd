## 1. 问题一：8K 底图和放大区域对不上

### 1.1 根因：两套坐标系差了一个 90° 旋转

| | 极轴方向 | 经度 0° 方向 | 经度 +90° 方向 |
|---|---|---|---|
| HEALPix / 天文坐标系（`healpix.js`、`lod.js` 全程使用） | **+z** | +x | +y |
| three.js 渲染坐标系（`THREE.SphereGeometry` 的等距圆柱贴图） | **+y** | +x | **−z** |

底图把经纬度铺在
`D_base(λ,φ) = (cosφ·cosλ, sinφ, −cosφ·sinλ)`
方向上（由 `three.core.js` 的 `SphereGeometry` 顶点公式
`x = −r·cos(phi)`、`y = r·cos(theta)`、`z = r·sin(phi)`，`uv = (u, 1−v)` 直接反解），
而 `tilePointVec()` 返回的是
`D_hp(λ,φ) = (cosφ·cosλ, cosφ·sinλ, sinφ)`。

两者相差一个**绕 x 轴 −90° 的旋转**：`D_hp = R_x(+90°) · D_base`。

`buildTileGrid()` 把 `tilePointVec()` 的输出**直接**塞进 `position` 属性，中间没有任何转换，
于是整层瓦片相对底图转了 90°：视野中心叠着的瓦片和底下底图根本不是同一块地形。

**同一个屏幕点上两层的经纬度（实测，浏览器内计算）：**

| | 经度 | 纬度 |
|---|---|---|
| 底图在该点显示的地形 | −45.00° | 0.00° |
| 瓦片在该点显示的地形 | 0.00° | 45.00° |

差 45° 以上。仅在 `lon=0, lat=0`（月面中心，正好是旋转轴）附近两者才偶然重合——
这也解释了为什么问题看起来"时好时坏"。

### 1.2 怎么确认的：三条互相独立的证据

**(a) 代码级** — 读了 vendored 的 `three.core.js` 里 `SphereGeometry` 的顶点公式，
和 `buildTileGrid()` 里"`tilePointVec` 输出直接 push 进 position"，两头都是确定的。

**(b) 资源级** — 确认 8K 底图确实是标准等距圆柱（`u=0 ↔ 经度 −180°`）：
在资源图上按标准公式取 `(-45°, 0°)` 附近 ±15° 的块，最亮的辐射纹环形山落在
经度 −38.4°、纬度 +6.6°，而 **Kepler 坑的真实坐标是 −38.0° / +8.1°**。

**(c) 渲染级** — 把 8K 资源按两种坐标系各自重投影到屏幕，再与 WebGL 实际输出做高通相关
（整球视角 d=5.25，1306×598 视口、DPR 2）：

| 视角 | 按渲染坐标系（y=极轴）采样 | 按天文坐标系（z=极轴）采样 |
|---|---|---|
| A（局部方向 (0.707, 0, 0.707)） | **r = +0.61** | r = −0.03 |
| B（局部方向 (0.04, −0.998, 0.025)） | +0.26 | −0.005 |

见 `fig-basemap-frame-convention.png`（三行分别是：渲染输出 / 按 y=极轴采样 / 按 z=极轴采样，
只有中间那一行和渲染输出对得上）。

### 1.3 修法

把坐标系转换收在**一处边界**上，而不是散在各处：

1. `healpix.js` 新增 `hpToRender()` / `renderToHp()`（互为逆的纯旋转）和
   `renderUv()`（渲染坐标系方向 → 底图等距圆柱 UV），并附上完整的推导与实测记录。
2. `tiles.js` 的 `buildTileGrid()` 把顶点从天文坐标系转到渲染坐标系。
   转换是纯旋转（det = +1），**不影响绕向**，原有的 `(a,c,d)/(a,d,b)` 索引模式仍然朝外。
3. `main.js` 在 LOD 边界做三次转换：相机位置、反投影方向（渲染系 → 天文系），
   瓦片四角方向（天文系 → 渲染系）。`lod.js` 与 `healpix.js` 内部保持纯天文坐标系不变。
4. `applyTestView()` 的 `?lon=&lat=` 改用渲染坐标系公式——**语义变了**：
   现在指的是真实月固经纬度（修复前指的是天文坐标系下的方向）。

### 1.4 验证

**(a) 数值** — 修复后同一屏幕点，底图与瓦片的经纬度**差 0.000°**。

**(b) 画面** — 见 `fig-registration-before-after.png`：

- 上排（修复前）：底图是一片糊的灰（因为瓦片没盖在你看的地方），瓦片却是另一块地形；
- 下排（修复后）：底图是模糊的第谷坑，瓦片是锐利的同一个第谷坑。

**(c) 相关** — 同一机位（d=1.35、第谷、相位 150）下
「瓦片层画面」与「纯底图画面」的相关：

| 低通半径 | 0 px | 5 px | 20 px | 40 px |
|---|---|---|---|---|
| r | +0.620 | +0.687 | +0.719 | **+0.742** |

见 `fig-registration-overlay.png`（红=底图结构，绿=瓦片结构，黄=重合；画面以黄绿为主）。

**(d) 回归测试** — `test/tile-geometry.test.mjs` 新增两条：

- `瓦片几何在渲染坐标系里（y = 自转轴），与底图球一致`：对 9 个用例（含极冠、各阶）
  检查**每个顶点**都落在"按底图经纬度算出的瓦片角尺度"之内；并要求 4 个以上用例具备
  区分两种坐标系的判别力（两种坐标系在 ±x 轴附近重合，那里的用例不计入）。
- `uv1 是底图那套等距圆柱经纬度`。

**变异验证**：把 `buildTileGrid()` 里的 `hpToRender()` 换回直通，测试从 62 过变成
**60 过 2 挂**（新用例 + 绕向用例同时报警），改回后恢复 62 过。

## 2. 问题二：放大后没有起伏

### 2.1 根因

`moonMat`（底图）一直挂着 LOLA 高程生成的法线贴图，而 `TileLayer` 的材质
**没有** `normalMap`。于是高清区的明暗只随理想球面法线变化，地形本身不产生起伏——
看起来就是"一张照片贴在球面上"。

### 2.2 修法

给瓦片材质接上**同一张** LOLA 法线，但有两个坑：

1. **UV 不同**。瓦片几何的 `uv` 是**图集坐标**（4096² 画布里的槽位），
   而法线贴图要按**等距圆柱经纬度**采样。做法：`buildTileGrid()` 额外写一路 `uv1`
   （由 `renderUv()` 从渲染坐标系位置算出），法线贴图设 `channel = 1`，
   Three.js 就会用 `uv1` 而不是 `uv`。切线帧由 Three.js 的 `getTangentFrame()`
   从 `dFdx(vNormalMapUv)` 解析求出，对球面 + 等距圆柱 uv 是精确的。
2. **纹理不能共用同一个 `Texture` 对象**（底图用 channel 0，瓦片要 channel 1）。
   做法：`moonMat.normalMap.clone()`。`Texture.copy()` 里 `this.source = source.source`，
   GPU 纹理按 `Source` 缓存，所以**显存里只有一份**（浏览器内实测
   `tileMat.normalMap.source === moonMat.normalMap.source` 为 `true`）。

接线路径两条都覆盖：法线贴图可能在 `initHips()` 之前或之后加载完，
所以 `initHips()` 里建完 `tileLayer` 会补一次，加载完成回调里也会补一次；
之后新建的图集页材质会自动带上（`TileLayer.setNormalMap()` 会记住）。
界面上"起伏"滑块现在同时改底图和瓦片（`setNormalScale()`）。

### 2.3 验证

- 滑块 0 ↔ 1.2 对照（近距 L7，见 `fig-relief-normalmap.png`）：
  中心 700×700 区域 **平均 |差| 5.9、p95 = 18、最大 86，52.4% 的像素变化 > 3**。
- 材质检查：`normalMap` 已绑定、`channel = 1`、`normalScale = 1.2`、
  几何 `uv1` 属性存在、与底图共用同一个 `Source`。

**必须说清楚的一点**：这是**影像**，不是地形。LOLA 法线贴图在全球只有约 1.9 km/像素，
所以它能恢复的是**大尺度起伏的光照**（盆地边缘、月海脊、大坑的环壁），
细到第谷坑中央峰那种尺度是没有真实高程的。7 m 分辨率的 DOM 不会带来 7 m 分辨率的地形。

## 3. 连带修正：亮度标定重算

上一轮的增益 5.0 是在**瓦片盖错半球**的状态下标的——测的不是同一块地形，不成立。

重标方法：固定机位（d=1.35、第谷、曝光 1.05），关掉细节层取底图均值为基准，
再扫增益读瓦片均值，找两者相等的位置。ACES 非线性，所以必须在渲染域反解。

| 月相 | 底图均值 | 零交叉增益 |
|---|---|---|
| 104°（应用默认） | 68.0 | **6.64** |
| 150° | 152.8 | 8.73 |
| 180°（满月） | 159.7 | 8.89 |

理想增益随月相漂移（亮部压缩 + 底图被放大后是模糊的，两者方差不同），
单一全局增益不可能同时命中。取 **7.5** 作**相对误差**的折中：

| 月相 | 残差 |
|---|---|
| 104° | +8.0% |
| 150° | −6.0% |
| 180° | −6.4% |

独立复核（另一支截图，相位 150、d=1.35）：瓦片均值 143.8 vs 底图 152.7 = **−5.8%**，
与预测的 −6.0% 一致。

## 5. 已知问题 / 未解决

按"会不会影响你实际观看"排序。

### 5.1 逐张瓦片的亮度离散，仍是全局折中

同一张瓦片相对底图同区域的所需增益在 **1.9 ~ 29** 之间（见
`docs/validation/coords/calibration.json`）。7.5 是全局中位折中，所以
区域性的亮度差依然存在；开启细节层时，月面像素里仍有 4%~31% 会变暗（最多 62 级）。
要真正消掉得做**逐张瓦片标定**（用底图对应区域归一化每张瓦片），本轮没做。

### 5.2 DOM 自带阴影 + 模拟光照 = 双重阴影

嫦娥二号 DOM 是摄影镶嵌产品，影像里本来就带真实阴影；我们再叠一路模拟太阳光照，
会出现"双重阴影"。这是数据集性质决定的，除非改成"不再打光、直接当自发光贴图"，
但那样又和底图的光照体系不一致。目前选择的是"与底图一致"。

### 5.3 7 m 影像 ≠ 7 m 地形

见 2.3。高清区得到的只是**影像**清晰度，地形起伏仍然来自 1.9 km/像素的 LOLA。
想要真实起伏需要 SLDEM2015（约 60~120 m/px，但只覆盖 ±60°，且体积以 GB 计）。

### 5.4 元数据请求没有超时

`fetchSourceConfigCached()` 没有传 `signal`（`fetchSourceConfig()` 支持 `signal`，
但调用方没用）。测试中遇到过底图正常、细节层一直停在"连接中…"且不报错的情况。
瓦片加载器有 25 s 超时，元数据这一步没有。**这是一行就能修的问题，本轮按"先不改"没有动。**

### 5.5 `moc_sky_fraction = 1` 是发布者声明

只抽样核验过数百张瓦片，不代表全月 314 万张都正确。且 `hips_frame = moon`
与站点自带的 Aladin Lite 页面（硬编码 `'equatorial'`）矛盾——**那个落地页是错的**，
客户端应信 `properties`。

### 5.6 改变过的视觉默认值

- 太阳光强度 `4.0 → 1.4`（上一轮）：原来的场景 35.6% 的像素在色调映射前超过 1.0，
  底图 84% 贴顶、相邻像素梯度中位数为 0（字面意义上的没有细节）。
- 亮度标定增益 `5.0 → 7.5`（本轮，原因见第 3 节）。

想恢复原来的高亮观感可以把这两个值一起回调，代价是近距离细节再次糊掉。

### 5.7 测试用例覆盖不到的部分

移动端档位（2048 底图、单页图集、并发 3）只做了参数级检查，没有在真实移动设备上跑过。

## 7. 复现步骤

```bash
cd public && python3 -m http.server 5173
npm test                      # 62 个用例
```

固定视角（`d` 为月球半径倍数，`lon/lat` 为月固经纬度）：

```
http://localhost:5173/?d=5.25&lon=0&lat=0&spin=0          # 整球，不应有任何瓦片请求
http://localhost:5173/?d=1.35&lon=-11.36&lat=-43.31&spin=0 # 中距 L4
http://localhost:5173/?d=1.05&lon=-11.36&lat=-43.31&spin=0 # 近距 L7（第谷）
```

浏览器侧自检（控制台）：

```js
const L = window.__luna;
L.hips.baseMag, L.hips.centerOrder, L.hips.tiles.length, L.hips.readyKeys.size
L.scheduler.getStats()          // requests / errors / retries / evictions / persistentHits
L.tileLayer.materials[0].normalMap.channel     // 1
L.moonMat.normalMap.channel                    // 0
L.tileLayer.materials[0].normalMap.source === L.moonMat.normalMap.source  // true，共用显存
```

**注意**：`python3 -m http.server` 不发 `Cache-Control`，浏览器会启发式缓存 ES 模块，
改动可能不生效。用 CDP `Network.clearBrowserCache` + `Network.setCacheDisabled` 后再测。
