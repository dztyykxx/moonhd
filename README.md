# LUNA · 超高清月球

three.js 实时渲染的月球探索器。**本地 8K 底图（LROC WAC）+ 按需拉取的嫦娥二号 7 m 高清瓦片（China-VO HiPS）
+ LOLA 真实高程光照 + 月面地名/坐标/经纬网交互**。静态站点，无构建步骤，无运行时依赖（three.js r186 已本地内置）。

```bash
cd public && python3 -m http.server 5173
# 打开 http://localhost:5173    （必须走 http，importmap 不支持 file://）
npm test                       # 97 个用例，纯 Node，不需要浏览器
node tools/build-places.mjs    # 由已核验的官方数据重建 public/data/*.json
```

操作：拖拽旋转 · 滚轮/双指缩放 · 单击月面选点 · 双击放大 · 快捷键 `H` 沉浸 · `Esc` 退出 ·
`A` 自转轴 · `G` 经纬网 · `R` 复位 · `Space` 自转 · `/` 搜索。

拖拽灵敏度**随缩放变化**，按"抓住月面"的规律：满屏拖拽转 `2·(d−1)·tan(fov/2)`，
在任意距离下都是 1:1 跟随（拖多少像素，月面就移动多少像素），并有 1.2°/满屏的下限
保证贴到最近时仍能微调。见 `geo/metrics.js` 的 `dragRotateRadPerScreen()`。

## 界面与地理交互

UI 按 `docs/design/luna-ui-design-spec.md` 实现，模块划分：

```
public/src/
  main.js              场景与相机（渲染管线未改架构）+ UI 桥接 api
  ui/app.js            DOM 控制器：面板、搜索、信息卡、可见性、快捷键、抽屉
  ui/visibility.js     可见性偏好（版本化 localStorage）+ 沉浸状态
  geo/coords.js        月固坐标契约：方向向量、格式化、输入解析
  geo/pick.js          屏幕射线 × 解析球面（不遍历瓦片）
  geo/graticule.js     经纬网/自转轴几何 + 间隔滞回
  geo/metrics.js       北向指示 + 局部比例尺
  scene/overlays.js    自转轴与经纬网的 three.js 对象（挂在 moon 下）
  data/places.json     44 个地点（27 地貌 + 17 着陆点），由官方数据生成
  data/moon-facts.json 月球概览参考值 + 来源
```

**坐标契约**：纬度北正南负、经度东正西负并规范化到 `[-180,180)`；渲染系 `dir = (cosφcosλ, sinφ, −cosφsinλ)`。
`geo/coords.js` 是唯一一套公式，并有测试把它钉在已与 astropy-healpix 对过的天文系上。

**三种坐标**：视野中心（屏幕中心射线与月球的近交点）· 指向位置（鼠标在月面上时更新，约 20 Hz，移到星空即清空）·
选中点（点击固定，独立于前两者）。选点与地名标签由三维位置投影，被月球挡住即隐藏。

**所有界面都能独立隐藏**：顶栏与搜索、地点目录、地点信息卡、底部坐标栏、观察工具栏、缩放工具、
地名与选点标记、自转轴与极点、经纬网与坐标标签。偏好按 `luna.ui.prefs`（版本化 schema）保存。
沉浸模式是**临时**状态，不覆盖偏好，退出后恢复原组合；恢复入口为 `H` / `Esc`，
或鼠标靠近底部 / 轻触空白处出现的"显示界面"按钮。全部隐藏后仍可用 `H` 唤回可见性面板。

**画质与数据面板**读取实际运行状态：底图分辨率、当前高清层级、可视瓦片数、帧率、内存与 IndexedDB 用量、
累计请求与命中数，全部来自运行时，不是设计稿样例。用户显式选择的档位记在 `luna.ui.quality`。

**模拟月相**：面板标题是"模拟月相"，固定标注"模拟光照，不表示今天的真实月相"。
`setPhase()` 只是调整场景光源角度（公式与历史版本一致，默认 104° 的画面不变）。
滑块是"光照角度"而不是天文相位角；四个预设的角度由模型固定朝向解出并在参考视角下逐档核对过画面
（新月 342.8° · 上弦 72.8° · 满月 162.8° · 下弦 252.8°），点预设会先把镜头带回正面参考视角。
"模拟光照比例"按当前镜头方向与光源方向的实际夹角实时计算，不是旧公式按滑块角度换算的百分数。

## 显示策略：默认只用底图，放大才拉高清

整球视角**一张瓦片都不请求**。只有底图在屏幕上被拉伸到"一个屏幕像素对应不到一个底图纹素"时，
才开始按需拉取当前视野的瓦片；缩回去自动释放，回到纯底图。

判定依据不是相机距离，而是**底图放大倍率** = 月球屏幕直径（设备像素）÷ 底图横向覆盖月球的纹素数。
这样窗口尺寸和 DPR 变化都会自动反映进来。进入阈值 1.0、退出 0.8（滞回，避免在阈值附近来回闪）。

| 视角 | 倍率 | 细节层 | 瓦片 | 瓦片请求 |
|---|---|---|---|---|
| 整球 d=5.25 | 0.19 | 关 | 0 | **0** |
| 中距 d=1.35 | 1.08 | `L4 · 57/57` | 57 | 57 |
| 近距 d=1.05 | 2.99 | `L7 · 66/66` | 66（2 页图集） | 66 |
| 缩回整球 | 0.19 | 关 | 0 | 0 |
| **重访同一近距视角** | 2.99 | `L7 · 66/66` | 66 | **0（全部命中本地缓存）** |

（1306×542 视口、DPR 2 实测。层级上限目前是 HiPS order 7 ≈ 28 m/px。）

## 渲染架构

球的几何只有一个（半径 0.997 的 `SphereGeometry` + `MeshStandardMaterial`，
通过 `onBeforeCompile` 注入彩色调制）。高清瓦片是**独立的曲面网格**
（半径 1.0，同样落在球面上），挂在 `moon` 节点下面跟随自转。

```
底图 diffuseColor = 8K 灰度反射率 × 彩色调制        （moonMat）
瓦片 diffuseColor = mix(底图色, 瓦片色 × gain, alpha)  （TileLayer 材质）
```

选瓦片层而不是"往底图上贴补丁"，是因为要同时满足：多层级共存（更细的没到时先显示粗的）、
逐张淡入、以及只画视野覆盖的那一小块球冠。

### 底图与彩色

`moon_albedo_{1k,2k,4k,8k}.webp`，1K 秒开再逐级升清。**逐级升清意味着这几张都会下载**
（1K 173 KB + 2K 672 KB + 4K 2.6 MB + 8K 11 MB）。加上彩色层 104 KB 和法线贴图 2.5 MB，
首次访问桌面端合计约 **17.5 MB**；手机端只升到 2K，合计约 **1.4 MB**。
嫌大的话可以改成只发 8K 一张，或按屏幕宽度只发对应档位。

彩色层 `moon_chroma_1k.webp` 在着色器里算
`tint = chroma / luma(chroma)` 再乘到灰度反射率上——亮度来自高分辨率灰度，
色相来自彩色层，两者解耦。

### 高清瓦片：HiPS + 图集 + 视锥选择

1. **LOD**（`hips/lod.js`）：从 12 张 order 0 瓦片开始的四叉树遍历。把瓦片中心与四角
   投到屏幕空间，只有"一张 512px 瓦片被放大到超过 620 屏幕像素"时才继续细分。
   父瓦片的可见性判定必须把**瓦片自身角半径**算进去，否则近距离时球冠整个落在父瓦片内部，
   一步都下降不了（曾经的症状：d≤1.10 时一张瓦片都选不出来）。
2. **图集**（`hips/tiles.js`）：4096² 画布放 8×8=64 张 512² 瓦片，一页一次 draw call。
   多页时**每页一个材质**（各持自己的 `tileAtlas` uniform，共享标定 uniform），
   按 `uv.page` 选——否则第二页的瓦片会采样到第一页同槽位的无关内容。
   `AtlasSlots` 存"分配"与"已画入"两件事，上传幂等（否则静止时也会有 243 次/秒的重复上传）。
3. **调度**（`hips/scheduler.js`）：按需请求、有限并发（桌面 4 / 手机 3）、
   失败重试封顶 + 熔断、内存 LRU（桌面 128 MiB）且**当前画面在用的瓦片被 pin 住**。
4. **持久化**（`hips/cache.js`）：IndexedDB，桌面 256 MiB。看过的区域再看一次是 0 网络请求。

### 坐标系：一处边界，两边分明

这是本项目踩过最大的一个坑，值得单独说明。

`healpix.js` / `lod.js` 内部全程使用 **HEALPix 天文坐标系**（z = 自转轴）；
而 three.js 这边（底图球、相机、`moon.matrixWorld`）用的是**渲染坐标系**（y = 自转轴）。
两者相差一个绕 x 轴 90° 的旋转：

```
天文 (X, Y, Z)  →  渲染 (X, Z, −Y)
```

转换只在 `main.js` 的 LOD 边界上做三次（相机位置、反投影方向、瓦片四角方向），
`tiles.js` 的 `buildTileGrid()` 负责把顶点落到渲染坐标系。
曾经漏掉这一步的症状就是"**8K 底图和放大后的区域对不上**"——整层瓦片被搬到了另一个半球。
完整推导与实测见 `docs/validation/phase3/report.md` 第 1 节。

### 地形光照

底图和瓦片共用同一张 LOLA 法线贴图（`moon_normal_5760.webp`）。
瓦片的几何 `uv` 是**图集坐标**，所以额外写一路 `uv1`（等距圆柱经纬度），
法线贴图设 `channel = 1` 按 `uv1` 采样；瓦片用的是底图纹理的 `clone()`，
`Source` 共享，**显存里只有一份**。

注意：7 m 的 DOM 是**影像**，不带 7 m 的地形。法线贴图全球只有约 1.9 km/px，
恢复的是大尺度起伏的光照，不是真实视差。

## 已知问题

1. **逐张瓦片的亮度离散**：各瓦片相对底图所需增益在 1.9~29 之间，界面上的"亮度标定"用的是
   全局折中值 7.5（实测最大残差 8%），所以高清区与底图之间**仍有轻微亮度台阶**。
   要真正消除需要逐张标定。
2. **双重阴影**：嫦娥 DOM 影像自带真实阴影，我们又叠了一路模拟太阳光照。
   除非改成不打光直接当自发光贴，否则无法避免。
3. **7 m 影像 ≠ 7 m 地形**：见"地形光照"一节。
4. **元数据请求没有超时**：`fetchSourceConfigCached()` 没传 `signal`，网络卡住时
   细节层会一直停在"连接中…"且不报错（瓦片加载器有 25 s 超时，这一步没有）。
5. **`moc_sky_fraction = 1` 是发布者声明**，只抽样核验过数百张瓦片，不代表全月都正确。
6. **移动端档位**（2048 底图、单页图集、并发 3）没在真实移动设备上跑过。
7. **月相不是天文历算**：只有场景光照角度，没有日期、天平动、视直径或次地球点；
   "模拟光照比例"用的是观察者看到完整半球的近似，相机贴近时会有偏差。
8. **地名只有 44 条**，不是全量目录；搜索是本地匹配，没有拼音与同义词扩展。
   月海坐标是官方目录给出的**近似中心**，不代表严格地质单元范围。
9. **嫦娥任务坐标来自 NASA/GSFC/ASU LROC**：中国官方站点本次无法访问，未能双源核验；
   Luna 9 的坐标 NSSDC 原文即为"approximately"。
10. **短高度窗口**（<620px）下右侧一次只显示一个面板，信息卡需要先关掉设置面板才能看到。
